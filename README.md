## Агентный процесс в GitHub

Агент работает через GitHub Actions и OpenCode. Каждый воркфлоу отвечает за
одну роль, у каждого — свои права и своя точка входа.

### Воркфлоу

| Воркфлоу | Чем запускается | Модель | Зачем |
|---|---|---|---|
| `opencode.yml` | комментарий с `/opencode` или `/oc` в issue или PR | `opencode-go/kimi-k3` | интерактивный вызов: исследовать, исправить, сделать PR |
| `opencode-triage.yml` | создан issue | `opencode-go/kimi-k3` | разбор новой задачи и постановка без правок кода |
| `opencode-review.yml` | PR opened / synchronize / reopened / ready_for_review | `opencode-go/kimi-k3` | авторевью без правок — только комментарии |
| `scheduled-audit.yml` | cron `0 3 * * *` и вручную через workflow_dispatch | `opencode-go/kimi-k3` | плановая проверка Lighthouse, результат в issue |

Везде одна модель: задачи проекта укладываются в её возможности, дешёвый
вариант здесь не выигрывает по деньгам заметно, а предсказуемость выше —
одна модель, одни и те же места поломки.

Где смотреть прогоны: вкладка
[Actions](https://github.com/greenfoxer/ai-for-developers-project-387/actions) —
у каждого воркфлоу своё имя, ссылка на конкретный прогон есть и в комментариях
агента. Прогоны `hexlet-check` — автотесты Хекслета, `release-please` — выпуск версий.

### Команды вызова

Набор команд задан явно параметром `mentions: "/opencode,/oc"` в
`opencode.yml`. Дефолт экшена совпадает с ним, но явное значение защищает от
того, что дефолт изменится в новой версии экшена.

### Петля и фильтр ботов

Ответ агента — это тоже комментарий, который содержит команду вызова. Без
фильтра агент отвечал бы сам себе: прогоны шли бы лавиной, сгорали бы минуты
Actions и токены. Поэтому во всех воркфлоу есть условие
`!endsWith(github.actor, '[bot]')`: события от ботов (включая
`github-actions[bot]` и `opencode-agent[bot]`) отсекаются. Дополнительно
`opencode-review.yml` и `opencode-triage.yml` проверяют тип автора PR или
issue, чтобы не реагировать на объекты, созданные самим агентом.

### Права

Права выданы по воркфлоу отдельно и не поднимаются до прав всего
репозитория — иначе агент получал бы доступ к тому, что для его задачи не
нужно.

- `opencode.yml`, `opencode-triage.yml` — `id-token: write` + `contents: read`.
  Аппаратная часть экшена сама обменивает OIDC-токен на права комментирования.
- `opencode-review.yml` — `issues: write` и `pull-requests: write` нужны для
  комментариев к PR, `contents: read` — для checkout. Агент по условию не
  создаёт коммиты и PR.
- `scheduled-audit.yml` — запись только на уровне job `analyze` и только
  `issues: write` (создать issue с итогами). На job `audit` прав нет, верхний
  уровень — `permissions: {}`.

### Сессии агента открыты

Репозиторий публичный, поэтому у всех воркфлоу задан `share: true`: сессия
агента доступна по ссылке вместе со своим контекстом (промптом, файлами,
решениями). Для публичного учебного проекта это осознанный выбор — сессию
можно показать как рабочий артефакт. Если проект станет приватным или контекст
нельзя раскрывать, `share` переключается на `false` в одном месте воркфлоу.

### Самооценка

- С первого прохода: issue #2 → PR #3 (трёхколоночный экран) — исследование и
  правка сделаны за два вызова, один коммит, PR принят без доработок.
- С итерациями: issue #4 → PR #5 (помесячный календарь) — четыре коммита:
  основная правка, регенерация документации контракта, доводка тестов
  (AAA-секции), исправление отступов после сборки проверок.
- Урок по процессу: плановый аудит дважды создал issue за один день (#7 и #8).
  Лечится в `scheduled-audit.yml` проверкой существующих issue перед созданием.
